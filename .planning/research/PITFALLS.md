## Section 1 — Brand & Visual Identity Pitfalls

### Pitfall B-01: Logo and Hex Assets Bloating the CRAN Tarball

**What goes wrong:**
`man/figures/logo.png` and `man/figures/logo.svg` land inside the CRAN tarball. `man/` is always shipped — it is NOT excluded by `.Rbuildignore`. A high-resolution PNG logo (300 DPI, 512×512 px) is typically 200–400 KB; a hex sticker SVG with embedded raster content can be larger. The v0.62.0 tarball measures 339 KB (confirmed from `EventStudy_0.62.0.tar.gz`). CRAN enforces an approximate 5 MB limit and flags large installed sizes with a NOTE. Any logo assets must not push the tarball above ~1 MB without documented justification.

**Why it happens:**
`man/figures/` is the standard pkgdown logo path per the pkgdown docs. Developers add the logo there following the documentation without realising it is tarball-included. SVG files generated by Inkscape/Figma and exported with embedded raster tiles are especially dangerous — a single SVG can be >500 KB.

**Warning signs:**
- `R CMD check --as-cran` emits: `checking installed package size ... NOTE: installed size is Xb`
- `du -sh man/figures/` reports > 100 KB total
- CI CRAN-check step fails with a size NOTE not present at the v0.64.0 baseline

**How to avoid:**
1. Keep `man/figures/` to the minimum required for pkgdown: one `logo.svg` (pure vector, no embedded raster, target <20 KB) and one `logo.png` at 120×139 px (the pkgdown standard size). Both must be hand-optimised with `svgo`/`optipng` before commit.
2. Put all high-res hex sticker source files (Inkscape `.svg` with bleed, 600 DPI PNG export) under `data-raw/brand/`. The `^data-raw` pattern is already in `.Rbuildignore` (confirmed) — this directory is never shipped.
3. After adding any file to `man/figures/`, run `R CMD build . --no-build-vignettes` and measure the tarball: `ls -lh EventStudy_*.tar.gz`. Fail the acceptance check if tarball size > 1 MB.
4. The pkgdown favicon lives in `pkgdown/favicon/` — this directory is excluded by `^pkgdown` already in `.Rbuildignore` (confirmed). Never move favicon assets into `inst/` or `man/`.

**Phase to address:** Brand & Visual Identity phase. Acceptance check: tarball size assertion in CI after every asset addition.

### Pitfall B-02: Non-ASCII Characters Triggering R CMD Check NOTEs

**What goes wrong:**
An SVG logo or pkgdown CSS file contains non-ASCII bytes — smart quotes, em-dashes, degree symbols, or accented characters in embedded font family names (`'Söhne'`, `'Helvéti­ca Neue'`). CRAN `R CMD check --as-cran` emits `NOTE: Found non-ASCII characters`. This NOTE appears on CRAN build machines (which use a stripped locale) but may be invisible locally if the developer's shell has `LANG=en_US.UTF-8`.

The existing codebase is already disciplined: `report_narrative.R` uses `\u` Unicode escape sequences so no raw non-ASCII bytes appear in source (confirmed at lines 281–282). This discipline must be extended to any new SVG or CSS that ends up in the tarball.

**Warning signs:**
- `grep -rP '[^\x00-\x7F]' man/figures/ R/ inst/` returns hits
- `tools::showNonASCII(readLines("man/figures/logo.svg"))` returns matches
- `R CMD check` NOTE: `Found the following file(s) with non-ASCII characters`

**How to avoid:**
1. After exporting SVG from any design tool, run `grep -rP '[^\x00-\x7F]' man/figures/logo.svg` and fix every hit — replace non-ASCII font names with CSS generic families (`sans-serif`, `monospace`).
2. Never put pkgdown extra CSS/JS into `inst/` — keep it under `pkgdown/` which is `.Rbuildignore`d. Files in `inst/` are tarball-included and checked for non-ASCII.
3. Add `grep -rP '[^\x00-\x7F]' man/figures/ R/ inst/` to the CI lint step and fail on any match.

**Phase to address:** Brand & Visual Identity phase — add as a pre-commit CI check.

### Pitfall B-03: pkgdown Logo/Favicon Path Breakage on Deployed Site

**What goes wrong:**
The pkgdown site builds locally but the logo or favicon returns 404 on GitHub Pages after deployment. The `_pkgdown.yml` `url:` field (`https://sipemu.github.io/eventstudy/` — confirmed) is used to generate absolute image paths in HTML. A mismatch between `url:` and the actual Pages URL causes every logo reference to 404. Separately, a stale `docs/` cache from a previous build (with a different logo path) persists after a partial CI rebuild.

**Warning signs:**
- Browser console shows 404 for `logo.png` or `favicon.ico` on the live site
- `pkgdown::check_pkgdown()` warns about missing referenced files
- `docs/` directory contains a `logo.png` from a previous design iteration whose path no longer matches `_pkgdown.yml`

**How to avoid:**
1. Always place the logo at `man/figures/logo.png` (120×139 px) and `man/figures/logo.svg`. pkgdown copies these to `docs/` automatically during `build_site()`.
2. For the favicon, use `pkgdown::build_favicons()` once — it generates all required sizes (16×16, 32×32, 180×180, etc.) from one source image and writes them to `pkgdown/favicon/`. Never create favicons manually.
3. After any logo change, run `pkgdown::build_site(preview = FALSE)` locally and verify `docs/logo.png` and `docs/favicon.ico` exist before pushing.
4. The `_pkgdown.yml` `url:` value must not change. It is referenced by the r-lib `pkgdown.yaml` GitHub Actions workflow established at v0.62.0.

**Phase to address:** Brand & Visual Identity phase. Acceptance check: `file.exists("docs/logo.png") && file.exists("docs/favicon.ico")` after a clean CI build.

### Pitfall B-04: SVG-vs-PNG Rendering Inconsistencies Across Surfaces

**What goes wrong:**
An SVG logo renders correctly in the browser pkgdown site but appears broken in: (a) the README on the CRAN HTML mirror (CRAN's static mirror does not render `<img src="logo.svg">` — it shows a broken image icon); (b) PDF vignettes (LaTeX cannot include SVG without external converters); (c) the GitHub README in dark mode (SVG `fill` colours that work on white backgrounds become invisible on dark backgrounds).

**Warning signs:**
- CRAN HTML mirror (`cran.r-project.org/web/packages/EventStudy/index.html`) shows a broken image where the logo should appear
- PDF vignette compilation fails with `pdflatex: cannot include SVG`
- Logo disappears in GitHub dark mode

**How to avoid:**
1. The README must reference `man/figures/logo.png` (PNG), never the SVG. Use the pkgdown-standard pattern as an HTML img tag for size control: `<img src="man/figures/logo.png" align="right" height="139" alt="EventStudy logo" />`.
2. Reference the SVG from `_pkgdown.yml` only (`template: logo: src: man/figures/logo.svg`), where it is rendered in the browser under controlled conditions.
3. CRAN-shipped vignettes (the 18 in `vignettes/`) must never reference image files from `man/figures/` — the existing 18 vignettes do not include logo images (confirmed); keep it that way.
4. For GitHub dark mode safety, ensure the SVG has a light background or uses `currentColor` appropriately. Test with GitHub's dark mode preview.
5. The hex sticker distribution format (for hex.codes.org) is SVG + 2× PNG (181×209 px); these belong in `data-raw/brand/`, not `man/figures/`.

**Phase to address:** Brand & Visual Identity phase. Acceptance check: README renders correctly on CRAN HTML mirror preview (view-source check).

### Pitfall B-05: README Badge/Image Links Breaking on CRAN vs GitHub

**What goes wrong:**
A README badge uses a relative path (`./man/figures/screenshot.png`) that resolves on GitHub but fails on the CRAN package page (which serves the README from a different URL base). Alternatively, a shields.io badge URL contains a dynamic query parameter that CRAN's HTML renderer escapes incorrectly. The `README.md` is already excluded from the tarball by `^README\.md$` in `.Rbuildignore` (confirmed) so CRAN does not ship it — but CRAN's web interface scrapes and renders it.

**Warning signs:**
- Badges show broken-image icons on the CRAN web page for the package
- `pkgdown::build_home()` produces warnings about unresolvable image paths

**How to avoid:**
1. For any screenshot or example image linked from the README, use an absolute URL pointing to the pkgdown site (`https://sipemu.github.io/eventstudy/reference/figures/...`), not a relative path.
2. Test README rendering with `pkgdown::build_home()` locally before pushing — it surfaces path issues.
3. Shields.io badge URLs should use the `flat-square` style (simplest HTML output) and avoid query parameters that might be HTML-escaped differently.

**Phase to address:** Brand & Visual Identity phase.

## Section 2 — Report & Plot Aesthetics Pitfalls

### Pitfall R-01: New Table/Theme Dependencies That Break PDF and Word Rendering

**What goes wrong:**
A plot theme or table styling function pulls in a new package (`gt`, `kableExtra`, `flextable`, `DT`) that works in HTML but either: (a) requires LaTeX packages not installed on CI/CRAN build machines for PDF output (`booktabs`, `longtable`, `colortbl`); (b) produces invalid DOCX XML for Word output that fails to open in Microsoft Word; or (c) is called without a `requireNamespace()` guard, causing `R CMD check` ERROR.

The existing `skeleton.Rmd` uses only `knitr::kable()` (confirmed at lines 221, 247, 277, 305, 328) — this is the correct baseline. Any aesthetic upgrade that introduces a new table package must preserve PDF/Word compatibility.

**Warning signs:**
- `R CMD check --as-cran` NOTE: `package 'gt' is not installed`
- PDF render fails: `Error: LaTeX package 'booktabs' not found`
- `DT::datatable()` inside a PDF chunk causes `Error: DT output format requires HTML`
- Word document fails to open in Microsoft Word after render

**How to avoid:**
1. Stay with `knitr::kable()` as the universal table primitive. For HTML-specific enrichment, add `kableExtra::kable_styling()` behind `if (knitr::is_html_output())` only. For PDF, `knitr::kable()` alone produces clean LaTeX tables. For Word, `knitr::kable()` outputs Markdown tables that pandoc converts.
2. `DT::datatable()` is HTML-only and must never be called unconditionally in `skeleton.Rmd`. Already in `Suggests` (confirmed in DESCRIPTION) — if introduced, guard with `if (knitr::is_html_output() && requireNamespace("DT", quietly=TRUE))`.
3. Any new table/theme package goes into `Suggests`, is `requireNamespace()`-guarded, and has a bare `knitr::kable()` fallback. Test the fallback explicitly in CI.
4. The `if (knitr::is_html_output())` switch already exists in `skeleton.Rmd` at lines 229, 253, 342 — extend it, never bypass it.

**Phase to address:** Report & Plot Aesthetics phase. CI must render all four formats (html, pdf, word, md) as integration tests; `test_es_report.R` should add multi-format render tests guarded by `skip_if_not_installed("tinytex")`.

### Pitfall R-02: Font Availability Regressions Across Platforms

**What goes wrong:**
A new ggplot2 theme uses a system or Google Font (`theme(text = element_text(family = "Inter"))`) that: (a) renders locally but falls back to `sans` on CRAN Linux build machines; (b) produces different figure dimensions (and thus different PDF page layout) when the fallback font metrics differ from the intended font; (c) requires `systemfonts`, `ragg`, or `showtext` as dependencies — `systemfonts` is a compiled package with FreeType/HarfBuzz system library requirements that vary across CRAN platforms.

The existing `plotting.R` uses only `ggplot2::theme()` with `element_text(hjust = 0.5)` and no font specification (confirmed at lines 185, 267). This is the correct baseline.

**Warning signs:**
- ggplot2 warning: `font family 'Inter' not found, using 'sans'` on CI
- Different figure aspect ratios between local macOS (Retina) and CI Linux (96 DPI)
- `R CMD check` on Windows: `DLL 'systemfonts' not found`
- PDF figure overflows page margin (font metrics wider than expected)

**How to avoid:**
1. Use only base ggplot2 font families (`"sans"`, `"serif"`, `"mono"`) in any function shipped in the CRAN package — these are always available on all platforms and produce consistent metrics.
2. Custom fonts are acceptable in: pkgdown article CSS (browser-rendered, not in the tarball), and in the HTML report's embedded CSS stylesheet. They must never appear in `R/plotting.R` or `skeleton.Rmd` knitr chunk options.
3. If introducing a `theme_eventstudy()` function in `R/plotting.R`, make it a thin wrapper over `ggplot2::theme_minimal()` that only adjusts colours and spacing. Do not add `systemfonts` or `ragg` to `Imports` or `Suggests` for this purpose.
4. Figure dimensions in `skeleton.Rmd`: the existing `fig.width = 10, fig.height = 6` (confirmed in the setup chunk) is fine for HTML but overflows US-letter PDF margins (text width ~6.5 inches). The aesthetics phase must add a per-format fig.width override in the setup chunk: `if (!knitr::is_html_output()) knitr::opts_chunk$set(fig.width = 6.5, fig.height = 4)`.

**Phase to address:** Report & Plot Aesthetics phase. Acceptance check: PDF render with minimal-tinytex CI; zero font warnings; all figures within text width.

### Pitfall R-03: `knitr::is_html_output()` Switch Broken by Non-Standard Format Objects

**What goes wrong:**
`knitr::is_html_output()` inspects `knitr::opts_knit$get("rmarkdown.pandoc.to")` which rmarkdown sets at render time based on the output format object. When `rmarkdown::render()` is called with a proper `rmarkdown::html_document()` etc. object (as `.build_output_format()` in `report.R` does — confirmed), this value is set correctly. If someone replaces `.build_output_format()` with an ad-hoc list that looks like a format object (a common copy-paste from older rmarkdown docs), `knitr::is_html_output()` returns the wrong value inside the template.

The consequence is plotly widgets embedded in a PDF render, which causes pandoc to fail with an error 99 or produces a PDF containing raw `<script>` tags as text.

**Warning signs:**
- PDF output contains visible `<script>` or `<details>` HTML tags as literal text
- PDF render fails: `Error: pandoc document conversion failed with error 99`
- `knitr::is_html_output()` returns `TRUE` inside a PDF chunk (detectable by logging `cat(knitr::is_html_output())` in a test chunk)

**How to avoid:**
1. Always use `rmarkdown::*_document()` constructor functions in `.build_output_format()` — never construct the format as a plain list. The existing implementation (confirmed) is correct; do not replace it during an aesthetics refactor.
2. Add a regression test: render `skeleton.Rmd` to PDF, then assert `!grepl("<script", readLines(output_pdf))`. (This test requires `pdftotext` or reading the PDF as binary and checking for the ASCII string.)
3. When adding any new plotly or DT call to `skeleton.Rmd`, always gate it with `if (knitr::is_html_output())` and provide a ggplot2 fallback — same pattern as lines 229/253/342.

**Phase to address:** Report & Plot Aesthetics phase — the `is_html_output()` gate is a hard invariant; regression test it before the phase is closed.

### Pitfall R-04: Per-Format Prose Sanitiser Silently Stripping or Mis-Escaping Content

**What goes wrong:**
The `.sanitise_prose()` function in `report_narrative.R` converts AI-generated text for each output format. Two failure modes:

1. **Over-aggressive:** The sanitiser strips a percentage sign (`12.5%`) in the LaTeX path, or converts a variable name containing `_` to `\_` twice (double-escaping), producing garbled output like `12.5` or `\_sigma\_`.
2. **Under-aggressive:** A `$` in AI-generated prose is not escaped for LaTeX, causing `pdflatex` to enter math mode and fail with `! Missing $ inserted`. An `&` not escaped for DOCX XML produces a Word file that fails to open.

The existing sanitiser already documents the ordering requirement (ampersand first, to avoid double-encoding — confirmed at lines 359–369 in `report_narrative.R`). Any new escape rules added for aesthetic polish must respect this ordering.

**Warning signs:**
- PDF render fails: `! LaTeX Error: Missing $ inserted` or `! Missing \endcsname inserted`
- PDF output shows `\_` or `\&` as literal text (double-escaped)
- Word document fails to open: "The file format or file extension is not valid"
- Percentage values display as bare numbers in PDF output

**How to avoid:**
1. Test the sanitiser against a comprehensive fixture corpus: `%`, `_`, `^`, `&`, `$`, `\`, `#`, `{`, `}`, smart quotes (`‘`, `’`, `“`, `”`), em-dash (`—`), en-dash (`–`), subscripts (`H₂O`).
2. Add parameterised snapshot tests for `.sanitise_prose()` covering all four format paths (`"html"`, `"pdf"`, `"word"`, `"md"`) against this fixture corpus. Add these to `test_offline_narrative.R` before touching the sanitiser code.
3. The rule ordering must remain: (1) ampersand, (2) remaining HTML entities for Word/MD, (3) LaTeX specials for PDF. Any new rule goes at the correct position in the chain — never before the ampersand rule.

**Phase to address:** Report & Plot Aesthetics phase — snapshot tests for the sanitiser are a pre-condition for any prose style changes.

### Pitfall R-05: Colorblind Safety and Figure DPI Regressions

**What goes wrong:**
A brand colour palette uses hue pairs that are indistinguishable under deuteranopia (~8% of males). Typical risk: green/red pairs for significant/non-significant results. A researcher with colour blindness cannot read the event-window significance bands.

Separately, changing `fig.width`/`fig.height` or `dpi` defaults in `skeleton.Rmd` without testing all four output formats causes: PDF figures overflowing margins (`overfull \hbox` in LaTeX log) or appearing blurry when Word output is printed (low DPI bitmaps).

**Warning signs:**
- `colorBlindness::cvdPlot(p)` shows indistinguishable lines under deuteranopia simulation
- PDF LaTeX log: `Overfull \hbox (X.Xpt too wide)`
- Word output: figures print at low resolution (< 150 DPI visible in Word's "Print Preview")
- Plotly plots for CAR/AAR visualisation use default red/green colouring for confidence bands

**How to avoid:**
1. Use the Okabe-Ito palette as the default for any new `theme_eventstudy()`: `c("#E69F00","#56B4E9","#009E73","#F0E442","#0072B2","#D55E00","#CC79A7","#000000")`. All eight colours are distinguishable under protanopia, deuteranopia, and tritanopia.
2. For the report template: add a per-format figure sizing block to the setup chunk. PDF-safe: `fig.width = 6.5, fig.height = 4`. Word print-safe: `dpi = 300, fig.retina = 2`. HTML: keep current `fig.width = 10, fig.height = 6`.
3. Add a Suggests-guarded colorblind check: `if (requireNamespace("colorBlindness", quietly=TRUE)) colorBlindness::cvdPlot(p)` in a developer-only diagnostic script in `data-raw/`, not in the package itself.

**Phase to address:** Report & Plot Aesthetics phase. Acceptance check: cvdPlot visual review of the new palette; PDF render with no LaTeX overfull warnings; Word print preview at 300 DPI.

## Section 3 — API & Message Polish Pitfalls

### Pitfall A-01: Silently Breaking Backward Compatibility via Renamed Arguments

**What goes wrong:**
A function argument is renamed for consistency (e.g., `output_file` → `file`, `confidence_level` → `alpha`, `interactive` → `plotly_interactive`) without a deprecation shim. The old argument name becomes part of `...` and is silently ignored. Existing user code gets wrong output with no error or warning — `es_report(task, output_file="my_report.html")` silently writes to the default path instead.

The exposed signature for `es_report()` (confirmed: `output_file`, `format`, `sections`, `provider`, `title`, `author`, `confidence_level`, `interactive`) and `generate_report()` must be treated as frozen. `plot_stocks()` exposes `target_variable`, `add_event_date`, `max_symbols`, `do_sample` (confirmed from `plotting.R`).

**Warning signs:**
- An existing vignette code block produces output at the wrong path after a rename
- The 2287-test suite passes but a smoke test of vignette code fails
- `R CMD check` produces: `'...' argument(s) 'old_arg_name' will be ignored`

**How to avoid:**
1. Never rename a public argument. If a new name is desired, add it as an alias via the `...` mechanism with an explicit base-R deprecation: detect the old name in `...` at the top of the function and warn with `warning("'output_file' is deprecated; use 'file' instead.", call. = FALSE)`.
2. Perform an argument-name audit at the start of the API Polish phase, before writing any code. Document which names are frozen and which are candidates for consistency cleanup. All cleanup goes through the deprecation shim path.
3. After the phase, verify: `identical(names(formals(es_report)), c("task","output_file","format","sections","provider","title","author","confidence_level","interactive","..."))` — add this as a regression test.

**Phase to address:** API & Message Polish phase. Acceptance check: smoke test every vignette code block in a clean R session.

### Pitfall A-02: print()/format() Method Changes Breaking Test Snapshots (and User Scripts)

**What goes wrong:**
A `print.EventStudySummary` or R6 `$print()` method is updated during the polish pass — adding a header line, changing column widths, improving formatting. Any testthat 3e snapshot test for that method fails immediately. More dangerously: if no snapshot test exists for the method (confirmed — the test suite currently has no `expect_snapshot()` calls except in `test_es_report.R`), the change ships silently but breaks downstream user scripts that call `capture.output(print(task))` and parse the text.

**Warning signs:**
- A `_snaps/` snapshot file diff appears unexpectedly in a git diff
- `capture.output()` parsing in a downstream script stops working after package update
- A user reports that their log file grep stopped matching after an upgrade

**How to avoid:**
1. Before changing any `print()` or `$print()` method, add a snapshot test: `expect_snapshot(print(task))` or `expect_snapshot(task$print())`. This locks the current behaviour.
2. When changing the output intentionally, update the snapshot via `testthat::snapshot_accept()` and document the change in `NEWS.md` under version `0.65.0`.
3. Treat the output of `print.EventStudySummary` (in `task.R`) as a public API surface — changes are minor version changes, not patch changes, if they alter text that users might parse.
4. If adding colour/styling via `cli`, ensure `withr::local_options(cli.num_colors = 0)` or equivalent strips ANSI codes in snapshot tests so the snapshot contains only semantic text.

**Phase to address:** API & Message Polish phase — add snapshot tests for all public print methods as the first task, before any method is changed.

### Pitfall A-03: Adding `cli` or `lifecycle` as Hard Import Dependencies

**What goes wrong:**
`cli` and `lifecycle` are popular packages for styled deprecation warnings and console output. Adding either to `Imports` (instead of `Suggests`) increases the hard dependency footprint for every EventStudy user. `lifecycle` imports `glue`; `cli` carries compiled C extensions. Neither is justified for a package whose core value is statistical correctness. The existing `Imports` list has 13 packages (confirmed in DESCRIPTION) — any growth will trigger CRAN reviewer attention.

**Why it happens:**
Developers reach for `lifecycle::deprecate_warn()` as "the right way" without checking whether base R `.Deprecated()` or `rlang::warn()` (already in `Imports`) suffices. They add the package to `Imports` for autocomplete convenience and forget to move it to `Suggests`.

**Warning signs:**
- DESCRIPTION `Imports:` grows beyond 13 packages
- `R CMD check` NOTE: `package 'cli' listed in Imports but installed size exceeds threshold`
- A clean install of the package installs `cli` transitively when the user did not ask for it

**How to avoid:**
1. Implement all deprecation logic using base R: `warning("'old_arg' is deprecated; use 'new_arg' instead.", call. = FALSE)` or `.Deprecated(new = "new_arg")`. The `rlang` package (already in `Imports`) provides `rlang::warn(message, class = "eventstudy_deprecated")` for classed conditions if machine-readability is needed — no new dependency required.
2. For styled console output in `print()` methods: use plain `cat()`. Do not add `crayon` or `cli` to `Imports` or `Suggests` for this purpose.
3. Post-phase acceptance gate: `length(strsplit(trimws(desc::desc_get("Imports")), ",\n?\\s*")[[1]])` must equal 13.

**Phase to address:** API & Message Polish phase.

### Pitfall A-04: `message()` vs `warning()` vs `stop()` Discipline Regressions

**What goes wrong:**
During API polish, a `message()` gets "upgraded" to `warning()` because it feels more important — but this breaks user code that uses `suppressMessages()` to silence it. Or a `warning()` is downgraded to `message()` in a context where users rely on `tryCatch(..., warning = function(w) ...)` to catch it. The hardening milestone (v0.50.0) established a documented discipline — polish must not erode it.

The existing grounding guard uses `warning()` for dropped ungrounded literals (confirmed in `report_narrative.R` and `advise.R`). The `generate_report()` multi-format skip uses `message()` (confirmed in `report.R` lines 365, 382). These distinctions are intentional and must not be changed casually.

**Warning signs:**
- An existing `suppressMessages()` call in a test suddenly allows a warning to propagate
- An existing `expect_warning()` test catches a message instead (or vice versa)
- `R CMD check --as-cran` notes: `unexpected output to stderr during examples`

**How to avoid:**
1. Before changing any `message()`/`warning()`/`stop()` call, search all test files for `expect_message()`, `expect_warning()`, `expect_error()` referencing the affected function.
2. Document the intended signal type in the function's roxygen `@details` or inline comment before changing it. Follow the established discipline: operational progress → `message()`; input quality concern → `warning()`; unrecoverable → `stop()`.
3. Add a dedicated test file `test_message_discipline.R` with `expect_message()` and `expect_warning()` assertions for the most user-visible signals: `es_report()` mode message, `generate_report()` format-skip message, grounding guard warning.

**Phase to address:** API & Message Polish phase.

## Section 4 — Docs & Site Polish Pitfalls

### Pitfall D-01: pkgdown Build Flakiness from Network Requests at Article Build Time

**What goes wrong:**
An article or vignette added during the docs polish phase calls `download_stock_data()`, `readRDS(url(...))`, or hits an external API. The CI pkgdown build (GitHub Actions `pkgdown.yaml` workflow, established at v0.62.0) fails on network timeout or rate limiting, producing a flaky build that is red on some runs and green on others. This directly violates the "all rendered articles execute fully offline" decision confirmed for v0.63.0 in PROJECT.md.

**Warning signs:**
- CI build is red on `pkgdown.yaml` but green on `R-CMD-check.yaml`
- The failing step is `pkgdown::build_articles()`, not `R CMD check`
- Error: `Error in curl::curl_fetch_memory(url): Could not resolve host`

**How to avoid:**
1. All articles in `vignettes/articles/` must use only bundled data: `data(dieselgate)`, `data(earnings_surprises)`, or synthetic data generated with `set.seed()`. These are the established bundled datasets (confirmed in `data/`). This constraint applies to every article added during the docs polish phase.
2. Before pushing any new article, run `pkgdown::build_articles(lazy = FALSE)` locally. If it requires network, fix it before the commit.
3. Set `options(timeout = 1)` at the top of any new article and wrap any `tryCatch(..., error = ...)` around any potentially network-touching call — if the call errors, the article must still render (use bundled fallback data).

**Phase to address:** Docs & Site Polish phase. Acceptance check: full `pkgdown::build_site()` run with no network available (can simulate with `options(timeout = 1)`).

### Pitfall D-02: Broken Cross-References in pkgdown Articles

**What goes wrong:**
An article references a function with `[es_report()]` or a cross-article link like `[Introduction](introduction.html)`, but after a filename rename during the polish pass, the link becomes 404. pkgdown silently drops unresolvable links rather than erroring — the article renders without the hyperlink and the build succeeds. The broken link is only discovered by a user navigating the site.

The current `_pkgdown.yml` navbar references specific article filenames (confirmed: `articles/introduction.html`, `articles/methods-return-models.html`, etc.) — any rename of an article file must update `_pkgdown.yml` simultaneously.

**Warning signs:**
- `pkgdown::check_pkgdown()` warnings about unresolved links (this is a manual step — it is NOT run automatically by `pkgdown::build_site()`)
- Navbar item produces 404 on the deployed site after a filename rename
- Browser console shows 404 for a cross-article link

**How to avoid:**
1. Run `pkgdown::check_pkgdown()` as a required CI step after every docs change — add it to the `pkgdown.yaml` workflow. It takes <5 seconds and catches broken navbar links and unresolved `@seealso` cross-references.
2. Treat article filenames as stable public URLs once deployed — never rename without adding a `_pkgdown.yml` `redirects:` entry.
3. Use `[function()]` pkgdown Markdown link syntax in articles — pkgdown attempts to resolve these and warns on failure. Prefer it over `\code{\link{}}` which silently degrades.
4. After any `_pkgdown.yml` navbar change, manually click every navbar item on the local preview (`pkgdown::preview_site()`) before pushing.

**Phase to address:** Docs & Site Polish phase — add `pkgdown::check_pkgdown()` as a CI step.

### Pitfall D-03: Articles vs Vignettes Tarball Leakage

**What goes wrong:**
A new article is accidentally placed in `vignettes/` (not `vignettes/articles/`) during the docs polish pass. The `^vignettes/articles` `.Rbuildignore` pattern (confirmed in `.Rbuildignore`) only excludes the `articles/` subdirectory. A file placed directly in `vignettes/` is included in the CRAN tarball, is built by `R CMD check --as-cran`, and can cause NOTEs (missing optional LaTeX packages, long render time) or WARNINGs (network calls in example code).

**Warning signs:**
- `R CMD check --as-cran` takes dramatically longer than the v0.64.0 baseline (was ~2 min)
- `R CMD check` NOTE: `vignette 'methods-return-models' is not available because Suggests packages are not installed`
- `tar -tzf EventStudy_*.tar.gz | grep vignettes` shows a new filename not in the baseline list of 18

**How to avoid:**
1. Every new rich article must go in `vignettes/articles/` — never directly in `vignettes/`. Before any commit, run `ls vignettes/*.Rmd` and verify the output matches only the known 18 CRAN vignettes.
2. After adding any file in `vignettes/articles/`, run `R CMD build . --no-build-vignettes && tar -tzf EventStudy_*.tar.gz | grep vignettes` to confirm the new article is absent from the tarball.
3. The `.Rbuildignore` entry `^vignettes/articles` must not be weakened to a specific filename pattern — it must cover the whole directory.
4. Add to CI: a tarball content check that diffs the vignette list against the baseline 18 files and fails if any new `vignettes/*.Rmd` appears.

**Phase to address:** Docs & Site Polish phase. Acceptance check: tarball content diff against the 18-vignette baseline.

### Pitfall D-04: DESCRIPTION Version and NEWS.md Out of Sync

**What goes wrong:**
The milestone starts without bumping DESCRIPTION from `0.64.0` to `0.65.0`. Multiple commits land. Then a CRAN submission is attempted with the correct version but NEWS.md still has no `# EventStudy 0.65.0` heading, or has an incompatible heading format. CRAN submission fails: `Version in DESCRIPTION: 0.65.0 does not match NEWS.md first entry`. Additionally, the pkgdown Changelog page (`reference/changelog.html`) renders stale content because `pkgdown::build_news()` uses NEWS.md.

**Warning signs:**
- `pkgdown::build_news()` renders a Changelog with no entry for `0.65.0`
- `devtools::check_win_devel()` flags a version mismatch between DESCRIPTION and NEWS.md
- `packageVersion("EventStudy")` returns `0.64.0` after the milestone is "complete"

**How to avoid:**
1. At the very start of the v0.65.0 milestone, before any code change, run `usethis::use_version("minor")` — this bumps DESCRIPTION to `0.65.0` and creates the `# EventStudy 0.65.0` NEWS.md scaffold in one step.
2. Each phase adds its own bullet points under the `0.65.0` heading in NEWS.md as part of its acceptance check — not deferred to end of milestone.
3. The `cran-comments.md` file (already present in the repo) must be updated with submission notes before CRAN upload.

**Phase to address:** First phase of v0.65.0 — version bump is the very first commit.

## Technical Debt Patterns

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|----------------|-----------------|
| Hardcoding `theme = "flatly"` in `.build_output_format()` | Quick HTML theming | Cannot be overridden by user without forking; must change everywhere when brand updates | Never — accept a `html_theme` argument with `"flatly"` default |
| Adding `cli`/`lifecycle` to `Imports` for polish messages | Better user experience | Heavier dependency tree; CRAN reviewer scrutiny | Never — use base R or `rlang` (already imported) |
| Storing hex sticker source in `man/figures/` | pkgdown finds it automatically | CRAN tarball bloat; non-ASCII NOTE risk | Never — use `data-raw/brand/` |
| Calling `plotly::ggplotly()` unconditionally in skeleton.Rmd | Richer HTML output | PDF/Word render failure; pandoc error 99 | Never — always gate with `knitr::is_html_output()` |
| Global `fig.width = 10` for all formats | HTML looks good | PDF margin overflow | Never in `skeleton.Rmd` — use per-format override in setup chunk |
| Skipping `pkgdown::check_pkgdown()` in CI | Faster CI | Broken links accumulate silently | Never — it takes < 5 seconds |
| Placing a rich article in `vignettes/` directly | Simpler file placement | Leaks into CRAN tarball; may cause R CMD check WARNINGs | Never — always use `vignettes/articles/` |
| Renaming public argument without deprecation shim | Cleaner API | Silent breakage in user scripts; invisible without error | Never — always add deprecation warning first |

## Integration Gotchas

| Integration | Common Mistake | Correct Approach |
|-------------|----------------|------------------|
| pkgdown logo path | Placing logo.svg directly in `pkgdown/` (excluded from tarball) without a `man/figures/` copy | Place both `man/figures/logo.svg` and `man/figures/logo.png`; reference from `_pkgdown.yml` |
| rmarkdown render + custom format | Constructing format as a plain list instead of `rmarkdown::*_document()` | Always use `rmarkdown::html_document()`, `rmarkdown::pdf_document()`, etc. |
| knitr::kable in Word | Using `kableExtra::kbl()` HTML-only features unconditionally | Gate all `kableExtra` HTML features behind `if (knitr::is_html_output())` |
| tinytex PDF in CI | Assuming tinytex is pre-installed on all GitHub Actions runners | `skip_if(!isTRUE(tinytex::is_tinytex()), "TinyTeX not installed")` in PDF tests |
| Plotly in PDF/Word | Expecting plotly to render via `always_allow_html: yes` | `knitr::is_html_output()` switch to ggplot2 for all non-HTML formats |
| NEWS.md heading format | Using `# EventStudy 0.65` (no patch version) | Use `# EventStudy 0.65.0` — CRAN checks exact version string match |
| SVG in README | `![logo](man/figures/logo.svg)` | `<img src="man/figures/logo.png" ...>` — PNG for universal rendering |
| Message/warning signals | Changing `message()` to `warning()` "because it's more important" | Check all test assertions on the affected function first; follow operational→message, concern→warning, fatal→stop discipline |

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| `knitr::opts_chunk$set(fig.width = 10)` globally | PDF figures overflow text width | Per-format fig.width override in setup chunk | Any PDF render |
| `pkgdown::build_site()` without lazy mode | Full rebuild on every CI push (slow) | `pkgdown::build_site(lazy = TRUE)` in CI for iterative runs | Not a correctness issue but wastes CI minutes |
| Large font/icon assets in `pkgdown/extra/` | Slow site loads; large `docs/` directory | Optimise SVGs with `svgo`; limit icon fonts to only used glyphs | Always — the pkgdown site must stay snappy |
| Snapshot tests without `withr::local_options(cli.num_colors = 0)` | ANSI codes in snapshot files; unstable across terminals | Strip colours in snapshot test setup | Any terminal with colour support |

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|---------------|----------------|
| Tarball bloat from logo assets | LOW | Move large assets to `data-raw/brand/`; rebuild tarball; confirm size |
| Non-ASCII NOTE on CRAN submission | LOW | `grep` and sanitise offending file; resubmit; one-line fix |
| Broken pkgdown logo path after deploy | LOW | Run `pkgdown::build_favicons()` + `pkgdown::build_site()`; push `docs/` |
| PDF render breaks (LaTeX special char in prose) | MEDIUM | Identify offending character in sanitiser fixture; add escape rule at correct position in chain; re-render all formats |
| Snapshot test failure from print method change | LOW | `testthat::snapshot_accept()` + NEWS.md entry |
| Renamed argument breaks user code | HIGH | Add deprecation shim; add NEWS.md breaking-change note; bump patch version to 0.65.1 |
| Article leaks into CRAN tarball | MEDIUM | Move to `vignettes/articles/`; verify `.Rbuildignore`; rebuild tarball; issue patch release |
| Flaky CI pkgdown build from network call | MEDIUM | Find offending `download_*()` call in new article; replace with `data(dieselgate)` or synthetic data; push fix |
| PDF figures overflow margins | LOW | Add `if (!knitr::is_html_output()) knitr::opts_chunk$set(fig.width = 6.5)` to setup chunk; re-render |
| `cli`/`lifecycle` accidentally in `Imports` | LOW | Move to `Suggests` or remove; add `requireNamespace()` guard; re-check |
